# Security

## Authentication and authorisation

* Every `/api/v1/*` endpoint except `GET /api/v1/health` requires an `Authorization` header using the bearer scheme with a configured token (the SSE client uses fetch streaming so the header is used there too).
* Tokens are configured in `EVALFORGE_API_KEYS` as `token:user_id:role` (comma separated; role `admin` or `user`). Compared with constant-time `compare_digest`. Use long random values (`openssl rand -hex 32`). If no key is configured, every protected request is refused (fail closed).
* `AUTH_DISABLED=true` is honoured **only** when `APP_ENV=development`.
* Reports, snapshots, PDFs, video jobs and videos are owned by the creating user; other non-admin users receive **404** (existence is not disclosed). Admins can access all. Schedules can be created/enabled/disabled/triggered by admins only.
* Projects and datasets are shared across authenticated users in this version (no per-project ACLs). Anyone authenticated can create a report for any project they can name; treat tokens accordingly.
* The browser keeps the token in `sessionStorage` (cleared on tab close). A 401 clears it. This is simple token auth, not a user-management system.

## Downloads

Files are streamed by the API from storage keys generated by the server (`kind/<uuid>.ext`, validated by regex and resolved inside `ARTIFACT_DIR`); no client-supplied path is ever opened. Responses carry `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. There are no public URLs; short-lived signed URLs are not implemented (authenticated streaming is used instead).

## Secrets

`MUBIT_API_KEY`, `TTS_API_KEY` and tokens live only in backend environment/`.env`. Nothing secret is in the repository, images, frontend bundle, snapshots, PDFs or videos. **Keys that were committed in the pre-3.0 history must be rotated** (see the audit).

## Input handling and limits

Pydantic validation on all bodies (lengths, enums, list sizes); metric/chart ids validated against the catalogue; Claude output validated against a schema and grounded; PDF/video text is drawn, never interpreted as markup from users beyond ReportLab paragraph escaping (`safe()` sanitising). Limits: Mubit token/input/rate budgets, `VIDEO_MAX_ACTIVE_PER_USER`, `VIDEO_MAX_DURATION_SECONDS`, `MAX_ARTIFACT_BYTES`, scheduler daily cap.

## Containers

Non-root user (uid 10001), `no-new-privileges`, all capabilities dropped (compose), bounded CPU/memory, secrets only via environment, health checks, graceful SIGTERM shutdown, persistent volume for `/data`.

## Known gaps

No rate limiting on the HTTP API itself, no audit log, no TLS termination (put a reverse proxy in front), no CSRF concern for bearer tokens but tokens are long-lived, SQLite file permissions rely on the volume.
